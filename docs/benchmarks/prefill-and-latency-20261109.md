# 冷prefill重复与短请求干扰

沿用公开源码输入、实际1017 tokenizer及原C4生产二进制，不重启模型或改变网关。11月8日的一次测量加上11月9日两次新缓存命名空间测量，每个长度合计3个样本，全部缓存命中0。

| 实际输入 | 三次首内容时间 | 平均首内容时间 | 平均输入处理速度 |
|---|---|---:|---:|
| 65,537 tokens | 7.039 / 7.101 / 7.046 s | **7.062 s** | **9,280.6 tok/s** |
| 262,145 tokens | 27.177 / 27.290 / 27.362 s | **27.276 s** | **9,610.8 tok/s** |

速度逐样本按实际输入除以TTFT计算，再取算术均值，包含前端、tokenization与通信。两种长度的速率范围分别为9,228.7～9,311.2和9,580.5～9,645.9 tok/s。三个近时段重复不能替代跨日、多种自然语料的分布评测。

随后对同一端点发送一个全冷262,145-token输入，在0.764秒后发送“仅回复OK”的短请求。两请求都完成，长输入TTFT为27.392秒，**短请求TTFT为26.721秒**，长输入缓存命中0。脚本确认短请求提交早于长请求首内容。

这证明长冷prefill会阻塞后来短请求。它不是完整多人尾延迟分布，也不能与竞品131K、不同流数的1秒结果计算直接倍数，但足以指出调度缺口。加速孤立prefill与让短请求及时得到服务是两件都重要的事。

复现入口：`tests/integration/probe_prefill.py`、`tests/integration/probe_prefill_interference.py`。使用独占资源窗口、明确端点与新的缓存命名空间；脚本不自动管理服务、不重试未知请求。逐样本数值和原始SHA见同名JSON。
